# Langues du site — état, architecture, limites

Trois langues sont annoncées par la charte du dépôt : français, japonais, anglais.
Ce document dit ce qui bascule vraiment, ce qui ne bascule pas, et pourquoi.

## Ce qui existait avant

- **Deux sources pour un même texte.** Un dictionnaire TypeScript
  (`src/lib/i18n/locales/*.ts`) et rien d'autre ; les fichiers JSON n'existaient
  pas. Une clé pouvait manquer en japonais sans que rien ne le signale : le
  chargeur retombait silencieusement sur le français.
- **Des volumes écrits dans les traductions.** « 826 épisodes » et
  « 1 300+ fiches » étaient recopiés dans les trois langues. Un épisode ajouté
  en base rendait les trois faux d'un coup.
- **Un faux sélecteur dans le pied de page.** Le texte « FR · 日本語 » n'était
  pas cliquable : il promettait une version japonaise que rien ne servait.
- **338 chaînes d'interface écrites dans le code**, réparties sur 129 fichiers,
  hors administration. Mesuré, pas estimé :
  `bun apps/site/scripts/i18n-audit.ts` écrit le retard dans
  `docs/plans/shenron/i18n-backlog.md`.

## Ce qui est en place maintenant

**Une seule source.** `apps/shenron/site/messages/fr.json`, `en.json`, `ja.json`. Le
type `Dictionary` est dérivé du fichier français : une clé qui manque en anglais
ou en japonais casse `bun run type-check`, elle ne se découvre plus en
production. next-intl lit ces mêmes fichiers, côté serveur comme côté client.

**Deux façons d'écrire un texte, une seule source de vérité.**

| Contexte | Outil |
|---|---|
| Texte dans un composant serveur | `<T k="wiki.canon.title" />` |
| Chaîne en prop (`aria-label`, `placeholder`) | `useT()`, dans un composant client |
| Composant client déjà « use client » | `useTranslations()` de next-intl |
| `metadata` d'une page | reste en français, voir plus bas |

**Le cache n'est pas sacrifié.** Le layout racine ne lit ni cookie ni en-tête :
le serveur rend toujours le français, c'est ce que le CDN garde. `<T>` est un
composant client feuille — à l'hydratation, il relit le dictionnaire et remplace
le texte par la langue choisie, sans rechargement et sans deuxième variante HTML.

**Le vocabulaire Dragon Ball est tenu hors de portée du traducteur.** Mesuré :
« Le Kaméhaméha de Son Goku » passé à Google revient en *The Goku Sound Camel*.
`src/lib/i18n/glossary.ts` remplace chaque nom connu par un jeton opaque avant
traduction et remet la graphie de la langue cible après — japonais pour le
japonais, romaji quand il est fiable. Le lexique (1 316 termes) est construit
depuis nos propres tables par `apps/shenron/site/scripts/i18n-glossary-build.ts` et versionné dans
`messages/glossary.json`.

Trois pièges y sont traités, chacun constaté sur les données réelles :

- **La casse fait le nom.** Toriyama a nommé ses personnages d'après l'épicerie :
  Acide, Carotte, Radis. Protéger « acide » figerait un adjectif ordinaire dans
  toutes les langues ; seule la capitale distingue le nom du mot.
- **Les accents diffèrent entre le site et la base.** Le site écrit
  « Kaméhaméha », la table stocke « Kamehameha ». L'appariement ignore les
  diacritiques mais conserve les positions, sinon la phrase se recolle de travers.
- **Un même nom pour deux choses.** « Vegeta » est un prince et une planète ; la
  romanisation de la planète est `Bejiita-sei`. Quand deux lignes revendiquent le
  même nom avec des graphies différentes, aucune n'est fiable : le terme retombe
  sur sa forme française, celle que le site imprime de toute façon.

**Les textes juridiques ne sont jamais traduits par une machine.** Les préfixes
`legal.`, `confidentialite.` et `licence.` sont recopiés du français par
`apps/shenron/site/scripts/i18n-translate.ts` et listés comme tels. Une politique de
confidentialité qui dit autre chose en anglais n'est pas une traduction, c'est un
second contrat que personne n'a écrit.

**Ce qu'un humain n'a pas relu est écrit noir sur blanc.**
`messages/.machine.json` liste les clés remplies par la machine. Fichier interne :
rien n'en arrive sur une page publique.

**Les noms d'entités exploitent les trois colonnes.** `src/lib/i18n/entity.ts`
décide, pour une locale, laquelle de `name`, `name_ja`, `name_romaji` s'affiche
en premier et laquelle vient en second, avec l'attribut `lang` correct pour que
la synthèse vocale ne prononce pas le japonais à la française.

## Commandes

```bash
bun apps/site/scripts/i18n-audit.ts             # ce qui reste écrit en dur
bun apps/site/scripts/i18n-glossary-build.ts --apply   # reconstruire le lexique
bun apps/site/scripts/i18n-translate.ts         # clés manquantes en en/ja
bun apps/site/scripts/i18n-translate.ts --apply # les remplir
bun test apps/site/tests/i18n*.test.ts
```

Le traducteur passe par `bxc google translate`, lancé depuis les sources
(`~/bxc/src/cli/index.ts` ; le binaire compilé est cassé pour le moteur
navigateur). Aucune clé d'API, aucun secret.

## Limites assumées

- **Une seule URL par page, donc une seule langue indexée.** Le choix vit dans un
  cookie, pas dans l'adresse : Google n'indexe que la version française et
  aucune balise `hreflang` n'est émise, faute d'URL à désigner. Passer à des
  routes préfixées (`/en/...`, `/ja/...`) ferait changer toutes les adresses
  publiques et le registre de destinations ; c'est une décision éditoriale, pas
  une correction technique.
- **`<html lang>` vaut `fr` dans le HTML servi**, puis suit la langue choisie
  après hydratation. C'est la contrepartie directe du cache.
- **Les `metadata` restent en français.** Elles sont produites une fois côté
  serveur pour le document mis en cache et pour l'indexation ; les traduire
  demanderait des URLs par langue.
- **Le contenu éditorial reste français.** Fiches du wiki, articles,
  transcriptions : ils sont rédigés en français en base. Le sélecteur de langue
  le dit en toutes lettres plutôt que de laisser croire à un wiki trilingue.
- **Le bot et le serveur MCP ne sont pas concernés.** Leurs textes Discord
  restent écrits en français dans le code.
