# Documentation pipeline

> Historical source references (2026-10-07): links to removed modules use verified Git revisions. These records do not establish a current CLI route or installed capability.

Documentation must answer what exists, who owns it, what remains, and what
proves completion. [PLAN.md](../../plans/ai/PLAN.md) is the only active product plan.
[Source of truth](./SOURCE_OF_TRUTH.md) defines the evidence required for a claim.

## Document classes

| Class | Location | Maintenance rule |
| --- | --- | --- |
| Product entry | `README.md`, `docs/README.md` | Keep short; link to current authorities and working entry points. |
| Current architecture and delivery | `docs/PLAN.md` (not in repo), `ARCHITECTURE.md`, `SOURCE_OF_TRUTH.md` | Update with decisions and implementation; label targets and observations separately. |
| Operational guides | `docs/guides/ai/INSTALL.md`, `CLI.md`, `config.md`, topic directories | Check commands against the actual binary and owning implementation. |
| Historical evidence | Dated audits, research and retained implementation reports | Keep revision, scope and limitations; link to the current plan when superseded. |
| Compatibility entry | Former plan paths such as `ROADMAP.md` and `plans/codex-oss.md` | Retain short redirects and referenced anchors; no second task list. |
| Generated | `docs/reference/ai/SUMMARY.md`, `docs/llms.txt` (not in repo), `docs/_root/` (not in repo) | Historical outputs of the retired `aphrody-summary` owner. Current repository indexes use `yolo ops docs generate`. |

## Editing workflow

1. Read the owning source and current plan. Use Aphrody CLI and AI surfaces
   first where they cover the task: inspect `aphrody --help`, then the relevant
   `git`, `ingest`, `docs`, `awesome`, `infra` or `web` command help. Record a
   missing command or unusable result before using a fallback. Never treat
   command availability, exit zero or generated prose as evidence of the
   requested behavior without examining the result.
2. Update the current authority once. Link operational guides to it rather
   than copying task lists, ownership registries or measurement tables.
3. Preserve useful historical evidence with its revision. Superseded plans
   from this consolidation remain available at repository commit
   `bb46076ce7ab57ea3af96486dbefc66392ef3562`; use pinned Git links or
   `git show` rather than duplicating their contents in another docs folder.
4. Retain inbound anchors or update every known consumer. The link scanner
   checks file existence and deliberately ignores fragments, so it cannot
   prove that an anchor still exists.
5. Regenerate and run documentation gates from the repository root:

```powershell
yolo ops docs generate
yolo ops docs generate --check
bun run docs:check-links
git diff --check
```

Review the actual command output and report failures with their scope.
Documentation-only work does not require broad runtime test reruns. A change
to behavior, a generator or a validation script needs its focused checks and
the owning repository's applicable gates.

## Historical generator behavior

[aphrody-summary](https://github.com/aphrody-labs/aphrody/blob/72551ef2a984838019724839a5e90a1ca204f50f/crates/ai/summary/src/lib.rs) previously built the Markdown
navigation and context output from the docs tree. It also mirrored selected
root files into `docs/_root/` (not in repo); generation happens before the `--check`
comparison, so `--check` can refresh those mirrors.

The scanner used by the generator skips dot/underscore-prefixed paths except
`_root`, and the copied `docs/aphrody-os` (not in repo) tree. Ordinary historical Markdown
is included in `llms.txt`; its presence does not grant it current authority.
Do not add another full historical plan merely to archive a replaced file.

The [infra ecosystem catalog](../../ecosystem/ECOSYSTEM.md)
is generated by its owning repository. Do not hand-edit it or regenerate it
as a side effect of documentation-only work here. When a capability changes,
coordinate regeneration with the infra owner.

## Writing and proof

Use English for technical documentation. Prefer concrete behavior, owner
paths and relative links. Separate measured latency from targets, warm from
cold starts, local inference from model downloads, and source checks from
installed application proof. Never promise zero latency or infer model
quality from protocol parity.

Keep hosts, ports, deployment units and topology in infra. Keep UI design in
[aphrody-ui](../../../m3/docs/products/_source/README.md). Record licenses and extraction
provenance in [THIRD_PARTY_CODEX.md](./THIRD_PARTY_CODEX.md) and the owning
component's attribution files. Documentation updates cannot confer OSS status
on a bundled component or its model weights.
